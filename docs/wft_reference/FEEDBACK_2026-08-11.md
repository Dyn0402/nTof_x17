## The five things that changed my picture while cataloguing

Read these first; the rest of the file is the item-by-item record.

1. **The simulation confirms Dylan's charge-spreading intuition and turns it
   into a structural criticism of the model.** The resistive layer is 515
   discrete ESL strips running **along y**, with 250 µm grooves that block DC
   transport across x. So the Y view gets genuine resistive sharing and the X
   view *cannot* — its ±1 sharing has to be drift diffusion. `wft` models both
   planes with one depth-independent `c1` plus an amplitude-only `kY`. See F6.

2. **`fit_joint()` — the two-plane fit the document describes in §22 — has zero
   callers.** It is not exported from `wft/__init__.py` and nothing in the repo
   invokes it. The executed chain is independent 1D fits, plus an
   off-by-default *selection* coupling. See F23.

3. **There are two implementations of the sharing kernel and the one that was
   kept is not the one with the per-plane time constant.**
   `wft/archive/rc_ladder_2026-07-31/` has `kTauY = 1.78` from a *direct
   measurement* (τ_X 230 ns / τ_Y 410 ns). The shipped `wft/` does not. §14.3's
   "has not been done" is true only of the shipped line. See F12.

4. **The absolute-timing idea (F26) is the highest-value item in the list and
   costs one plot to test.** `ftst` already demonstrably carries real timing
   phase — `measure_dt_xy` separates det3 into two clean classes, −7.65 and
   −16.01 ns. A per-event t0 prior of σ ≈ 4.5–5 ns is available (paddle jitter
   ⊕ the 10 ns ftst quantisation) and unused. It will **not** move the headline
   resolution — see F26 for that correction — but it collapses the t0 axis of
   the §21 global start scan, which pays for the §21.1 p₀ widening, and it is
   the strongest available constraint on near-vertical planes.

5. **Several "should we?" items are already built and switched off, or already
   measured.** t0 is *already* continuous (F20). The lp zero-pad is *already*
   fixed (F17). Line-free 3-D cluster displays *already* exist (F9). Hit-rate
   dead-strip finding *already* exists, just not wired into `wft` (F1).

## Part I — the raw material (§1–4)

### F1 · Dead strips — identify them, and let them be wildcards
> *"How do we treat dead strips? Can we identify them by their pedestals and hit
> distribution before each run (carefully, I think hit distribution is probably
> better) and take these into account for our reconstruction algorithm? In some
> sense use them as wildcards, explaining a bad prediction if there is no charge
> where we think it should be?"*

**OPEN — real gap, cheap fix, and the machinery already exists.**

`wft` has no dead-strip concept. `io.strip_position_map()` returns NaN only for
channels that are *unmapped* (cabling), and `extract_window()` drops
non-finite positions. A channel that is mapped but dead enters the fit window
with a normal σ and zero signal, so the model is penalised for predicting
charge there — a systematic pull on p0 and w, exactly as suspected.

Hit-distribution is the right discriminator and pedestal is not: a broken
connection downstream of the preamp still produces a perfectly normal pedestal.
That machinery is already written — `beam_track_finding.py:296
find_dead_strips()`, per-strip hit rate across all events, dead = below 50 % of
the median rate at amplitude ≥ 500 (`DEAD_STRIP_RATE_FRACTION`,
`DEAD_STRIP_AMP_THRESHOLD`). It is not wired into `wft`.

The "wildcard" framing maps onto machinery that also already exists: the
saturation censoring in `chi2_plane` (`model.py`, the `ok = ~sat` mask). A dead
strip is the same kind of object with an *even weaker* claim — drop it from the
χ² sum entirely, with no penalty in either direction. Roughly a ten-line change
in `prep_plane`/`chi2_plane` plus a per-run mask in the bundle.

### F4 · Is the pedestal taken from a dedicated run?
> *"The algorithm is using the dedicated pedestal distribution taken separately
> from each run, right?"*

**ANSWERED — no, and the assumption is worth correcting.**

`wft/io.py:58–73`: the pedestal is the per-channel **median over the first 300
events of the physics run itself** (`N_PED_EVENTS = 300`). The noise σ is
1.4826 × MAD over those same 300 events, after common-mode subtraction. No
dedicated pedestal file is read anywhere in `wft`.

Dedicated pedestal runs do exist (`cosmic_bench/pedestals/`, and the DAQ's
`mm_processor` computes post-CNS pedestal RMS per run), so this is a choice, not
a limitation. The median is chosen precisely *because* those 300 events contain
real tracks.

Two consequences, both small and both unmeasured: the MAD-based σ is slightly
inflated on strips that see many tracks in the first 300 events, and pedestal
drift within a long run is not tracked at all. A one-off comparison against the
dedicated pedestal run for the same detector would settle both.

### F5 · Can common-noise subtraction eat a wide track?
> *"Can common noise subtraction be problematic for wide tracks? If we start to
> approach 64 strips I worry we might actually be throwing out signal? Maybe
> implement some check for this in the reconstruction algorithm?"*

**ANSWERED for cosmics — measured, and it is not a problem. OPEN for n_TOF.**

CNS is a per-sample median over each 64-channel Dream block (`io.py:70,94`).
A median only fails when *more than half* the block carries signal.

Measured on the det3 saturday run (7,093 events, `events.parquet`):

| | median | p90 | p99 | max |
|---|---|---|---|---|
| seed cluster strips, X | 6 | 10 | 18 | 33 |
| seed cluster strips, Y | 6 | 10 | 20 | 41 |
| fit window strips (incl. 3+3 pad), X | 12 | 16 | 25 | 80 |

So a typical cosmic occupies ~6 of 64 channels; even at p99 it is under a
third. Two further points work in the same direction: cluster strips are
contiguous in *position*, and channel order is not position order, so a
physically contiguous cluster is generally split across several 64-channel
blocks — which helps rather than hurts.

The worry is right for a different regime. On n_TOF the gamma flash and
multi-track events push occupancy far higher, and there CNS could genuinely eat
signal. Proposed guard, cheap and self-validating: per event and per block,
count channels above kσ; if the count exceeds ~25/64, flag it and recompute the
common mode from the *non-signal* channels only (one iteration: CNS → identify
signal → re-CNS). Worth building before n_TOF, not before MPGD26.

## Part II — why a per-strip time is not a drift time (§5–9)

### F6 · Charge should spread along the resistive strips, not across them
> *"I was expecting charge spread along the resistive strips but not
> perpendicular to them. I got the sense this wasn't totally what we were using
> in the reconstruction algorithm? However now with the simulation hopefully we
> have a better idea of what is going on and what to expect, even if we can't
> totally solve it yet."*

**OPEN — the intuition is correct, the simulation makes it a quantitative
prediction, and together they are a structural criticism of the current
kernel. This is the most important physics item in the list.**

The simulation's picture (`design/RESPONSE_SIM_PLAN.md §1`, "Orientation and
sharing anisotropy"):

- The ESL resistive strips **run along y**. Resistive (DC) transport therefore
  moves charge *along y*, and the 250 µm inter-strip grooves **block transport
  across x**.
- Charge moving in y lands on different **y-measuring** strips, so the **Y view
  sees genuine resistive sharing** — stronger and slower.
- The **X view cannot get resistive sharing at all.** Its ±1 sharing must come
  from transverse diffusion over the 30 mm drift, prompt induction, and weak
  inter-strip capacitance.

Three independent measurements agree with the asymmetry, and two more close off
the alternatives:

| evidence | value | source |
|---|---|---|
| direct copy-shape fit on near-vertical det3 tracks (n ≈ 1000/plane) | **τ_X ≈ 230 ns, τ_Y ≈ 410 ns**; kY 1.8–2.9 | `mx_june_wft/ANALYSIS_STATE_2026-07-31.md §2.1` |
| det3 direct kernel measurement, ±1 peak-time shift | +37 ns (X) vs **+87 ns (Y)** | reference doc §14.2 |
| avalanche footprint at the ESL | **σ₀ ≈ 33 µm**, ~24× smaller than the 780 µm pitch, barely voltage-dependent | S3 campaign, `RESPONSE_SIM_PLAN §5` |
| point-charge prompt induction to ±1 | **≈ 0** — in the checkerboard the nearest ±1 pad is 1.10 mm diagonal, the prompt kernel is ~0.2 mm | `RESPONSE_SIM_PLAN §3` (T2b) |
| Stage-B, untuned, tracks uniform in z | **c1_X = 0.202** vs measured 0.23–0.28, and c1_X **rises 0.005 → 0.239 across z, a factor 45** | `RESPONSE_SIM_PLAN §7` |

That last row is the falsifiable part: had X-view sharing come from the
avalanche footprint or from induction geometry it would be **flat in z**. It is
not. Diffusion is the X-view mechanism, by elimination and by direct
calculation.

**What this says about `wft`.** The model carries a depth-independent discrete
kernel `c1` (± an amplitude-only `kY` on Y) *and* a diffusion term `Dp·√u`, and
assigns the same functional form to both planes. If the simulation is right,
the X-view ±1 sharing *is* essentially the diffusion term and should scale
strongly with depth, so a constant `c1` on X is mis-attributing the same
physics twice.

Two things that have always looked like pathologies read differently in that
light:

- The calibration degeneracy (§35) drives `c1_X → 0` with `sigma_p0` inflating
  to compensate — on det7 to `c1 = 0.004`, on det4 to `0.067`. The document
  treats this as a failure mode to be pinned away.
- Under the RC-ladder kernel, `c1` sits on its 0.05 floor and *raising* it
  monotonically destroys the angles; "the data genuinely want very little
  discrete sharing" (`ANALYSIS_STATE §10.3` point 3).

Both are what you would see if the discrete X kernel were the wrong object.
That does not make the pinned-`c1` recipe wrong — it works, and it is what
produced every good number in the document — but it suggests the recipe is
succeeding by forcing a well-behaved wrong parameterisation rather than by
being right. Worth testing directly: a depth-dependent X-view sharing term
against the constant one, on det3, judged by the implied-velocity flatness
(§8.1) rather than by χ².

## Part III — the forward model (§10–18)

### F11 · Why k = 18 time slices?
> *"Why k=18 time slices?"*

**ANSWERED, with a caveat the document does not carry.**

18 bins × 60 ns = 1080 ns; at v = 36.6 µm/ns that is 39.5 mm against a 30.0 mm
gap (§11). The headroom is deliberate: it lets the fit place charge *past* the
physical cathode rather than piling it against a wall, which would bias t0.
`set_depth_bins()` extends the basis at low drift field where the column takes
longer than the window.

The caveat: **18 is a det3-at-1000-V number, not a universal one.** At the
fleet's slower chambers the K = 18 basis was measurably too shallow, and the
fleet was refit at K = 22 (`ANALYSIS_STATE §10.4`: det2's column endpoint moved
1206 → 1230 ns, det7's 1266 → 1418 ns). §53.1 lists `K = 18` in the constants
table without that note. K should be derived from v and the gap, not fixed.

### F12 · X and Y should have different kernel models, not just a kY scaling
> *"It seems like the x and y orientations should have different waveform kernel
> models, not just a kY scaling. Do you agree? Is this feasible to implement? I
> was hoping that the MX17_Geant simulation would really hand these to us but it
> hasn't gotten there yet (maybe never will)."*

**Agreed, and it is more built than the document says.** §14.3 already flags an
amplitude-only `kY` as unable to represent a copy that is both stronger and
~2× later — "a per-plane `tau_s` is the identified next structural improvement
and has not been done." That is true of the **shipped** `wft/` only.

`wft/archive/rc_ladder_2026-07-31/` is a second, independent implementation of
the same physics that **has** it:

| feature | what it does |
|---|---|
| `kTauY` | per-plane lateral RC constant. Measured **τ_X 230 ns / τ_Y 410 ns** on det3, ratio 1.78 |
| `tau2_fac_y` | the ±2 copy arrives at `fac·tau`; 4.0 on Y models RC *diffusion* (delay growing quadratically with distance) rather than linear delay |
| `sigma_sY` | per-plane template smearing |
| `MODEL_FRAC` | fractional model-error term in the χ² weights (production used 0.03) |

Read `wft/archive/rc_ladder_2026-07-31/README.md` before touching this — it
explains that the same feature was built twice, that the shipped version was
kept at the 2026-08-06 merge because it was the newer line and the one SPS ran
on, and that **neither is a superset of the other**. The archived copy has the
per-plane constants; the shipped copy has the more careful RC-tail treatment
(F17) and a runnable test. The direct measurement fits the observed copy 14×
(X) and 54× (Y) better than the old delay-and-smear form.

So: feasible, and mostly a merge rather than new physics. But F6 raises the bar
— if X and Y have different sharing *mechanisms* and not just different time
constants, a per-plane τ is the minimum and a per-plane kernel *form* (X
diffusion-dominated and depth-dependent, Y an RC line) is the physically
motivated target.

### F13 · Calibrations should be as constant as feasible
> *"I assume we're on the same page, but calibrations should be constant as much
> as feasible, with few free parameters to just fit with. Maybe some variation
> detector to detector. Hopefully the recent analysis of det4 at sps with the
> simulation in mind can help with this."*

**Agreed — and it is already the document's stated policy (§35.1).** Recording
what is and is not known to be transferable, because the boundary is sharper
than the document states:

*Constant* — the sharing kernel is a **property of the resistive layer**, with
three independent legs: invariant across a 6 % gain step, across drift fields
of 92–233 V/cm, across gas (Ar/iso on the bench vs wet Ar/CF₄/iso in the beam),
and across cosmics vs beam delivery (§51).

*Not constant, and must be re-measured per run* — `v_drift` (the beam gas was
4–5× slowed by percent-level water); the RC time constants **as represented in
a finite window** (F19); and `kY`.

One caution on the det4/SPS route: det4 is the fleet's worst chamber to
generalise from. 62 % of it does not amplify (fixed ~35 mm stripes), its
connectors were historically plugged inverted, and its free-fit calibration is
the degenerate example in §35. Its *beam* kernel measurement at normal
incidence is excellent and is what pinned c1/c2 — but its bench calibration
constants are not a fleet template.

### F14 · Can the forward fit use finer than 60 ns depth bins?
> *"Can we do finer than 60ns bins for the forward fit? Or does that give us no
> gain since we compare to 60ns spaced points?"*

**ANSWERED — and there is a code fact worth knowing first.**

The bin width is currently **not a free parameter**: `wft/model.py:84–86` sets
`DT = float(cal.sample_ns)`, so the depth-bin width is bound to the sample
period by construction, and `UK` follows. Decoupling them is a small change.

On whether it would gain: the design matrix is 736 × 18, nowhere near
rank-limited, so finer bins are not numerically forbidden — this is not the
naive "you can't beat your sampling" argument. The real limit is that a
template with a ~180 ns peaking time cannot resolve structure faster than its
own rise, so the extra columns will be near-degenerate, NNLS will sparsify
harder, and the profile gets noisier. Expected gain on p0 and w: small.

Expected *cost* is the part to watch: the profile summaries (`q_u50`, `q_u90`,
`q_uend`) feed the cathode/gap map (§50), and §19.1's trap is exactly that
sparse NNLS profiles break naive summary estimators. Anything that changes bin
width changes sparsity and would need the column estimator re-validated.

Verdict: one afternoon's ablation at DT = 30 ns is worth it for the answer; not
a priority.

### F15 · Explain the erf in the charge-spread parameterisation
> *"When we write this up I don't understand the erf error functions in the
> charge spread parameterization, if that survives it'll have to be explained to
> me."*

**CLOSED — write-up task; the explanation is short.**

`strip_fractions()` (`model.py:203`) answers one geometric question: bin *k*'s
charge is spread transversely as a Gaussian centred on the track line — what
fraction of it falls inside strip *i*'s 0.78 mm pitch?

The integral of a Gaussian between two limits is the difference of its
cumulative distribution at those limits, and the Gaussian CDF *is* the error
function (up to scaling). So

    F_ik = ½ [ erf((p_i + pitch/2 − p_c)/√2σ) − erf((p_i − pitch/2 − p_c)/√2σ) ]

is nothing more than "area under the Gaussian between the strip's two edges".
No erf-specific physics; it is the closed form for a Gaussian integral.

The interesting part is the width, which is three things in quadrature:
`sigma_p0` (the cloud before it drifts anywhere), `Dp·√u` (diffusion, growing
as the root of drift time), and the bin's own transverse span / √12 (the track
moves sideways during its own 60 ns; on a steep track this dominates).

### F16 · Is sigma_p0 the mesh-to-resist avalanche size? Does it depend on gas?
> *"Is sigma_p0 the mesh to resist avalanche size? Does that depend on gas?"*

**ANSWERED, and the simulation contradicts the fitted value.**

`sigma_p0` is the transverse width of the charge cloud at u = 0 — everything
that is *not* drift diffusion. That is the primary ionisation's transverse
extent plus the avalanche's transverse spread in the 150 µm amplification gap.
So yes, that is roughly the "mesh to resist avalanche size", and yes it is
gas-dependent in principle (transverse diffusion in the amplification gap is a
gas property).

But it has been measured in simulation: **σ₀ ≈ 33 µm at the ESL** (S3 campaign,
`RESPONSE_SIM_PLAN §5`), 24× smaller than the 780 µm pitch and barely moving
with voltage. The det3 bundle carries **`sigma_p0` = 0.242 mm** — about 7×
larger. det4's delay-mode calibrations reached 0.42–0.47 mm.

The document already names this parameter as "the one that absorbs model
error" (§12 trap) and uses an inflated `sigma_p0` as one of the three
degeneracy signatures (§35). The simulation now supplies the number that says
how much of it is real: almost none. That makes pinning `sigma_p0` physical the
better-motivated arm of the §35.1 recipe, and it is a concrete input the
simulation *has* delivered.

### F19 · The forward model should not be sensitive to tail cuts
> *"Ideally for the forward model we can find a universal model that is not
> sensitive to tail cuts. It seems possible as long as we're anticipating it,
> hopefully not a large hurdle."*

**Agreed on the goal; the document names the obstacle precisely and it is worse
than "be careful".**

§14.2's trap: the RC constants are **representation-dependent**. Beam
full-window fits give τ ≈ 300–800 ns; the bench's 1.92 µs window gives
τ ≈ 108–141 ns *for the same physics*, because the bench never sees the far
tail. Transplanting the beam's τ and its amplitudes into a bench bundle was
tried (arm B, 2026-08-05) and made things distinctly worse — `kY` collapsed to
0.59 and χ² rose 16 %.

The simulation hits the same wall from the other side: the integrated-charge
ratio between channels is *mathematically invariant* under any linear
time-invariant filter, so an apparent shaping-dependence of c1 was pure window
truncation — and "the area budget is only comparable to data when integrated
over the same window the DAQ uses" (`RESPONSE_SIM_PLAN §7`).

So the fix is not care; it is a change of parameterisation. Parameterise the
kernel by a window-independent physical quantity — the sheet transport
D = 1/(ρ_s·c′(d_k)), which is what the simulation's S1 solver produces — and
derive the window-truncated τ per configuration rather than fitting it. That
also makes the beam↔bench transfer well-defined instead of an experiment.

### F20 · t0 is quantised to 5 ns — can we go to 1 ns?
> *"The t0 is in 5ns precision – can we go to 1ns? What's the cost? Any gain?"*

**CLOSED — production t0 is already continuous.**

5 ns is a **cache grid**, not the fit's precision. `_time_tensors()` caches the
three response tensors on a 5 ns t0 grid because building them is the expensive
part; `chi2_plane(..., snap_t0=True)` snaps to that grid during the *coarse*
searches only. `build_matrix()` (`model.py:222–229`) interpolates exactly when
t0 is off-grid, and the final Nelder-Mead calls `chi2_plane(..., snap_t0=False)`
(`model.py:325, 334`). So the reported t0 is continuous and there is nothing to
gain.

**One exception, and it is the place it might matter.** The ref-pinned path
(`fit_plane_raw(..., fix_p0w=...)`, `model.py:298–307`) — used by the
calibration stages and the χ²(v) drift-velocity scan — scans t0 on a 20 ns grid
then a 5 ns grid and stops, with no Nelder-Mead refinement. There t0 really is
quantised to 5 ns. Given that v is measured through that path, checking whether
a finer final step moves v is cheap and worth doing once.

### F21 · Saturation modelling needs substantial work
> *"Saturation modeling needs substantial work. I think maybe we can fit the
> non-saturated points as normal. Then, for the saturated pulse we can try to
> extrapolate (similar to what we do in the mm_dream_reconstruction code)? Then
> fit the extrapolated points with a large error. As is, the saturated pulses
> were being underestimated."*

**Agreed, the diagnosis is right, and the reference implementation is located.**

Current behaviour (`model.py`, `chi2_plane`): clipped samples are **censored** —
dropped from the χ² sum, with a one-sided penalty if the model falls *below* the
clipped value. Conservative and correct as far as it goes, but it discards the
information, and the document's own failure table agrees: "saturation →
flat-topped core, angle biased; censoring helps; a saturation recovery model
would help more" (§44.1). "Saturation recovery rather than censoring" is
already in §55's open list.

The extrapolation being remembered is
`~/CLionProjects/mm_strip_reconstruction/waveform_analysis/src/WaveformAnalyzer.cpp:916`,
`WaveformAnalyzer::saturatedLinearExtrapolation()`: least-squares slope and
intercept over up to `satSlopeFitSamples` on each side of the clipped region,
then the intersection of the two lines gives the peak sample and amplitude,
with a fallback if either slope has the wrong sign.

The proposal — recover, then refit with a large error — is right and is a
strict improvement on censoring, with one refinement: the recovered value is a
**lower-bounded** quantity, so its uncertainty is asymmetric. Feeding it back
with a large *symmetric* σ would let the fit pull the peak back down, which is
the failure censoring was introduced to avoid. Give it an asymmetric penalty,
or keep the one-sided term and add an upper arm from the extrapolation.

Also worth confirming before building on it: `SAT = 3550` ADC against a 4096
full scale. That threshold should be checked against the real clipping
behaviour of the chain, not assumed.

### F22 · Strip-to-strip gain vs (x, y) position gain
> *"I think strip to strip gain was implemented, which I don't think makes as
> much physical sense as (x, y) position gain. Any way to implement this or too
> expensive? 1D gain might not be bad especially along the direction of the
> resistive strips and maybe if the mesh forms a wave square to the detector."*

**The physics reasoning is right; the current answer is "gain is not the
limiting systematic — but that was measured on det3 only."**

`prep_plane()` divides each strip's waveform and noise by a per-channel factor.
Measured spread on det3: **1.4–1.5 % over 452 channels**, and the ablation study
found that removing the gain map *entirely* changes per-event angles by less
than the statistical noise. Bundles therefore ship unit gains (§17). On det3,
neither per-strip nor per-(x,y) gain is a limiting systematic.

Elsewhere it plainly is. det4 has fixed ~35 mm non-amplifying stripes covering
62 % of the chamber — a position effect that no per-strip map on the *other*
plane can express. And the simulation **predicts** a genuine position-dependent
response independent of gain: the resistive pitch is 800 µm against the readout's
780 µm, so the ESL-to-pad registration phase advances 20 µm per pitch and repeats
every **31.2 mm** (39 resistive strips = 40 readout pitches). That is a
position-dependent *sharing kernel*, not just a gain, with a superperiod in x —
and the intuition about "1D along the direction of the resistive strips" is
exactly the right symmetry: nothing varies along y, the registration phase
varies across x.

Cost is low — a 1D map is one extra array in the bundle plus an index lookup.

The first move is not to implement it but to **look for the 31.2 mm beat** in
det3's residuals and sharing. It is a genuine prediction of the simulation;
finding it would be a real result, and finding it absent constrains the model.

### F23 · A 2D simultaneous model for X and Y
> *"What about a 2D simultaneous model for X and Y? It seems like we do this in

## Part IV — fitting one plane (§19–24)

### F24 · How are the constrained 18 charges actually solved?
> *"Yeah don't totally understand the constrained 18 charges – can you explain in
> the final document how we actually solve those? I get the linearity."*

**CLOSED — write-up task.**

For any trial (p0, w, t0) the model is linear in the charges: `model = M·q`. The
solve is **non-negative least squares** — minimise ‖(M q − y)/σ‖² subject to
q_k ≥ 0 — by the Lawson–Hanson active-set algorithm (`scipy.optimize.nnls`):

1. Start with every charge at zero and every constraint "active".
2. Compute the gradient; move the variable that most wants to go positive into
   the free set.
3. Solve the *unconstrained* least-squares problem on the free set only.
4. If any freed variable came out negative, backtrack along the line to the
   constraint boundary, re-activate whatever hit zero, and repeat step 3.
5. Stop when no active variable wants to leave. The algorithm terminates in a
   finite number of steps.

The visible consequence is **sparsity**: bins that "want" to go negative land
on exactly zero rather than near it. That is not a numerical artefact, it is
the constraint doing its job — and it is the §19.1 trap, because a per-bin
median over a sparse profile truncates, which is what produced the fake 24.7 mm
drift column and nearly got a chamber disassembled.

### F25 · Elaborate on the profile likelihood and the nuisance parameters
> *"Also please elaborate on the profile likelihood and nuisance parameters used
> here"*

**CLOSED — write-up task, with three caveats worth stating honestly.**

For Gaussian noise, χ²(p0, w, t0) = min over q ≥ 0 of ‖(M q − y)/σ‖² is a
**profile** χ²: the 18 charges are nuisance parameters *profiled out* (replaced
by their conditional best fit at every trial geometry), not marginalised. That
is what reduces a 21-parameter problem to a 3-parameter search, and it is exact
because the profiling is a closed-form solve rather than an approximation.

Errors then come from the curvature of that profiled surface — `_errors()`
(`reco.py:87`), finite differences with dp = 0.05 mm and dw = 2×10⁻⁴ — scaled
by √(χ²/dof) so that model imperfection *inflates* the error instead of being
ignored, then added in quadrature with the measured physics floors
(`FLOOR_TAN` = 0.018 ≈ 1.0°, `FLOOR_P0_MM` = 0.33 mm).

Three things the write-up should say plainly:

1. Profiling over an **inequality-constrained** nuisance breaks the usual Wilks
   asymptotics at the boundary. With sparse profiles many q sit exactly at zero,
   so the effective number of degrees of freedom is not 18 and the χ² surface is
   not exactly parabolic there.
2. t0 is profiled *jointly* with p0 and w by Nelder-Mead, but the reported error
   is taken from a **(p0, w) curvature only** — so the strong p0–t0 correlation
   the document highlights in §20 is not fully propagated into `p0_err`.
3. The measured pull widths are 1.19 (X) and 1.13 (Y) — about 20 % optimistic,
   which is the right size and sign for (2). Saying that in the write-up is
   better than quoting the pull alone.

## Part V — from a plane to an event (§25–30)

### F26 · The cosmic bench has absolute timing from the scintillator coincidence
> *"Ah for the timing, are you aware in the cosmic bench that everything on dream
> is triggered by 2 60x60 scintillators firing in coincidence, with ~5ns time
> resolution? Then our arrivals on the detector are fixed in their time windows
> (taking the fst into account) to that ~5ns. This is important because it means
> we really have absolute timing for the muon tracks passing."*

**OPEN — and on the evidence I can see, the highest-value item on the list. It
is currently not exploited at all.**

Present state: t0 is fitted freely, per plane, per event. §20 warns that p0 and
t0 are strongly correlated and that "t0 must be fitted freely and never fixed
from an external clock". That warning was written about fixing t0 to a
*bundle-level constant* — not about a real, per-event external clock.

If the trigger is the scintillator coincidence at ~5 ns, then
t0 = trigger time + fixed electronics latency + mesh-charge transit, and the
only per-event unknown left is the phase of an asynchronous trigger against the
60 ns DREAM clock. **That phase is what `ftst` records** (10 ns units).

The evidence that `ftst` carries real timing phase is already in the document:
`measure_dt_xy()` (§36) groups t0x − t0y by ftst class and gets two clean,
distinct offsets on det3 — −7.65 and −16.01 ns. If ftst were noise that grouping
would produce one blurred number.

So a per-event t0 **prior** is available and unused.

#### How tight, in practice

Dylan (2026-08-11), and this is the important part: **the ~5 ns is *measured* on
the cosmic bench, reading out the actual scintillators — so it already includes
everything** in the scintillator chain (PMT transit spread, discriminator,
time-walk, cables). It is the **pair** figure; a single paddle is somewhat
better.

That matters because it removes the only unbounded term. Taking 5 ns as the
width of the paddle-to-paddle time-difference distribution, σ_pair = √2·σ_single
gives σ_single ≈ 3.5 ns, all-inclusive.

| contribution | σ | note |
|---|---|---|
| scintillator chain, end to end | **≈ 3.5 ns** | from the measured 5 ns pair figure. ≈ 2.9 ns if the trigger edge is the *later* of the two, which is what a simple AND gives (max of two Gaussians, σ ≈ 0.83 σ_single). Walk and discriminator are **inside** this number |
| `ftst` quantisation | ≈ 2.9 ns | 10 ns units, uniform → 10/√12. **May already be inside the 5 ns** — depends on how it was measured (see below) |
| muon transit / path spread across a 60×60 paddle | ≲ 1 ns | negligible |

**σ_t0 ≈ 3.5–4.5 ns**, the range spanning whether the clock quantisation is
inside or outside the measured figure. Either end is comfortably tight enough
for everything in "what it buys" below, so the ambiguity does not need resolving
before starting — and check (b) measures the total directly anyway, which
supersedes this table.

#### What it buys — corrected

An earlier version of this note claimed the prior "breaks the p0–t0 degeneracy"
and would therefore tighten position. **That overstated it.** The degeneracy
direction is δp₀ = w·δt₀, so at w = 0.008 mm/ns (tan θ ≈ 0.22) a 5 ns prior
tightens p₀ by 0.04 mm, against a measured `FLOOR_P0_MM` of 0.33 mm. At the scan
edge (w = 0.021) it is still only 0.1 mm. It will **not** move the headline
position (core σ 0.46 mm) or angle (σθ 1.18°) numbers, and §42's ~1.0° floor is
per-bin transverse centroid jitter, which no timing constraint touches.

State that expectation up front, or the item gets run, σθ does not move, and it
is written off as a failure.

What does hold up:

1. **It collapses the t0 axis of the global start scan.** `_global_start()`
   stage 1 is a 7 × 11 = 77-point grid over (p₀, t₀) — p₀ over ±2.5 mm in 0.5 mm
   steps, t₀ over ±120 ns in 40 ns steps. A 5 ns prior turns 11 t₀ points into 1.
   That frees the budget to **widen the p₀ window**, which is §21.1 — the
   document's own top open item, 21 % of planes starting outside the box at 5×
   the catastrophic-failure rate. The prior does not merely help that fix; it
   pays for it.
2. **Near-vertical planes**, where the charge sits on one or two strips, timing
   carries almost all of the slope information, and the free slope wanders (σθ
   degrades to 1.42° X / 2.35° Y below |tan θ| = 0.04). The prior is strictly
   *stronger* than the joint fit here: `fit_joint` only ties t0x to t0y and
   leaves the shared value free, whereas an external clock pins it. The two are
   complementary, and the prior subsumes part of what §22 claims.
3. **It is a constraint from outside the detector** — unlike everything else in
   the queue it adds information rather than redistributing it.

Implementation is small: a Gaussian penalty ((t0 − t0_pred)/σ_t0)² added to
`chi2_plane`, with t0_pred calibrated per ftst class exactly as `dt_xy` already
is.

#### The gate, and how to read it

Two checks, in order.

(a) Confirm the trigger for the runs in question really is the scintillator
coincidence, and find out whether an ftst correction is already applied
somewhere in the chain (`qa_config.py`, the run config, the analyzer). The
time-resolution work established that the bench has a scintillator trigger and
an applied ftst — find that record first; it may settle the question without new
work. The one detail worth pinning down there is **how the 5 ns was measured**:
if the scintillator times were themselves read out through the DREAM sampling,
the clock quantisation is already inside the 5 ns; if through a separate
TDC/digitiser, it is not. Do not spend long on it — it is the difference between
σ_t0 = 3.5 and 4.5 ns, and (b) measures the total regardless.

(b) Plot the **spread of fitted t0 within a single ftst class** over many
events, at fixed geometry.

**Read it against the fit's own t0 resolution, not against an absolute
threshold.** An earlier version of this note said "~10 ns ⇒ real, ~100 ns ⇒
dead"; that is wrong, because the observed spread is the trigger jitter
*convolved with the fit's own t0 uncertainty*, which is not small. The correct
comparison:

- spread ≈ the fit's own t0 uncertainty ⇒ the trigger term is unresolvably
  small and the prior can be as tight as the budget above allows. This is the
  **good** outcome, and read naively it looks like a null result.
- spread ≫ the fit's own t0 uncertainty ⇒ the excess, in quadrature, *is* the
  real per-event jitter. Use it as σ_t0 directly — a measured budget beats the
  table above.

**Prerequisite:** `PlaneFit` reports `p0_err`, `w_err` and `tan_err` but **no
`t0_err`** — `_errors()` (`reco.py:87`) takes curvature in (p₀, w) only. The
diagnostic needs a t0 uncertainty, so extend `_errors()` to three parameters
first. Worth doing regardless: it is also the missing piece behind caveat (2) in
F25, where the p0–t0 correlation is not propagated into `p0_err` at all.

### F27 · Break the track's sliding degeneracy along its own line
> *"Can we break the track sliding efficiency along the line of the track? Maybe
> centering it in the drift volume or using a calibration of near-mesh
> efficiency/amplitudes?"*

**OPEN — same degeneracy as F26, plus a second, independent handle.**

Sliding a track along its own line trades p0 against t0, which is exactly the
correlation §20 shows. F26's external clock is the clean way to break it.

The second handle is already computed and used for something else: the charge
column must **start at the mesh and end at the local gap**, and `q_uend` is
already an output used to map the cathode (§50). Making that an explicit soft
constraint — the column spans [0, gap(x,y)/v] — is the "centre it in the drift
volume" idea, and it is straightforward as a penalty term.

The caution is circularity: the gap map was itself derived from these
reconstructions. Either keep it as a *validation* rather than a constraint, or
apply it only where the gap is independently known (det2 reads a flat 30.5 mm
and is the control chamber).

The "near-mesh efficiency/amplitudes" version is the weaker of the two — it
requires the depth dependence of collected charge to be calibrated, and §18
explicitly designs that dependence *out* of the model by letting q_k float per
bin. Adding it back as a constraint would give up a genuine strength (the model
currently *measures* the depth profile rather than assuming one).

### F28 · The algorithm must extend to two-track events
> *"Critical – we need to make sure in the end that this algorithm can also
> reconstruct 2 track events. I think we just separate track seeds and run the
> algorithm on all, then rank the results. But yes this is very important for
> ntof, obviously. Though don't really expect it or need to focus on it in

**OPEN — agreed on the priority and on the architecture. Half of it is already
built; the missing half is a named open item.**

The document is explicit that the model cannot represent two tracks (§18: "one
line, one charge profile… fitted as a compromise between them") and that δ-ray
or second-track is the dominant high-χ² failure mode (§44.1).

The proposed architecture — separate seeds, run the fit on each, rank — is
`fit_plane_candidates()`, which already fits up to `N_CANDIDATES = 3` clusters
and keeps the best. Making it keep *several* is a return-type change, not new
physics (`return_all=True` already exists internally).

Three genuinely missing pieces:

1. **A scale-free score.** §27's open item: Δχ² is computed inside each
   candidate's own window, so a bright compact cluster outscores a dimmer
   extended one regardless of which looks like a track. Two fits cannot be
   ranked against each other until this is fixed. This is a prerequisite for
   two-track, not a nicety.
2. **Two tracks inside one cluster.** Spatially separated tracks are handled by
   the candidate machinery; overlapping ones need either a two-line model or an
   iterative fit-and-subtract. The model's linearity in charge makes
   fit-and-subtract natural.
3. **X↔Y pairing with N > 1.** The classic combinatorial ghost problem, and the
   place where `select_pair`'s t0 coincidence stops being a refinement and
   becomes essential.

The suggested validation is the right one and is cheap: because the model is
linear in charge, **superimposing two real single-track events' waveforms
produces a physically correct two-track event with known truth**. No simulation
needed for the first pass.

### F29 · A more dynamic / smarter spark veto
> *"We need a more dynamic/smart spark veto"*

**OPEN — agreed. The current one is a flat count and is coupled to the wrong
thing.**

`SPARK_VETO_HITS = 50` (`seed.py:26`) drops an event if more than 50 strips
fire. Its known weakness is in the document itself: §25 says coherent noise
"fakes the spark veto", which the significance floor fixed — i.e. the veto is
sensitive to the upstream threshold rather than to sparks.

Better observables, all available with no new data:

- **Charge, not count.** A spark is a large charge on many strips; a steep muon
  is a modest charge on many strips.
- **Time structure.** A discharge is coincident across the chamber; a track is a
  ladder. The forward fit's own `q_uend` plausibility window (250–1100 ns)
  already encodes this and is currently only used for candidate selection.
- **Fraction of live strips, not an absolute count.** 50 out of how many?

Important constraint from the dedicated spark work: det3's sparks are
**muon-induced** (4× enhanced) and **edge-dominated**. So a veto that simply
cuts harder on multiplicity will preferentially remove real high-angle muons at
the chamber edges — the exact population the micro-TPC angle measurement
depends on. Any new veto must be checked against efficiency-vs-angle, not just
against spark rate.

### F30 · The fixed 12 mm gap split
> *"Same for the fixed 12mm gap split – don't want to rely too heavily on these
> fixed cuts"*

**OPEN — agreed, with one caveat in favour of keeping it where it is.**

`GAP_THRESHOLD_MM = 12.0` (`seed.py:24`), inherited unchanged from the

stay comparable between the two chains** (§25, §48). That is a good reason to
keep the production cut in the *seed*, and a bad reason to keep it as the only
clustering available to the fit.

For scale: 12 mm is ~15 strips at 0.78 mm pitch, and a real track at
|tan θ| = 0.25 spans ~7.5 mm across a 30 mm gap. So 12 mm is roughly one track's
worth — not crazy, but angle-blind and gap-blind.

Suggested shape of the fix: keep the production-matching cluster for the
efficiency bookkeeping, and add a second, angle-aware clustering pass whose
output goes only to the fit. That way the cut can be improved without silently
moving the efficiency numbers.

### F31 · At least 3 strips — can we recover below that for head-on tracks?
> *"Looks like we're requiring at least 3 strips, can we recover under that for

**OPEN — agreed, and it is cheap. The document already contains the argument

`MIN_STRIPS = 3` (`seed.py:25`), rationale "below that there is no ladder to

### F32 · Robust isochronous rejection
> *"Can we implement robust isosynchronous rejection?"*
> — **confirmed 2026-08-11: isochronous.**

**OPEN, but small — the discriminator already exists as an output; it is only
used internally and is not written anywhere you can cut on.**

Isochronous rejection means dropping events whose charge arrives essentially
simultaneously on every strip — a *flat* time ladder rather than a sloped one.
That is what a coherent-noise burst, a discharge and the n_TOF gamma flash all
look like. (A genuinely perpendicular track also has a flat ladder in
*position*, but not in *duration* — see below, that is what separates them.)

#### What `q_uend` is

`q_uend` is one of four summaries of the fitted charge profile
(`_profile_summary()`, `reco.py:70–84`). Recall the fit returns 18 non-negative
charges q₀…q₁₇, one per 60 ns depth bin, where bin *k* holds the charge that
arrived at drift time u_k = (k + ½)·60 ns after the mesh charge. So the profile
**is** the charge-versus-drift-time curve, and it is the shape of the drift
column the muon left behind.

The four summaries, all in nanoseconds after t₀:

| output | definition | reads as |
|---|---|---|
| `q_sum` | Σ q_k | total collected charge |
| `q_u50` | drift time at which the cumulative profile reaches 50 % | median arrival — "the middle of the column" |
| `q_u90` | same at 90 % | where the column is nearly finished |
| **`q_uend`** | centre of the **last bin still above 5 % of the profile's peak**, plus half a bin | **the end of the column** — how deep the gas was still delivering charge |

So `q_uend` is a *duration*: it is how long, after the first charge arrived from
the mesh, the detector was still receiving charge. Multiply by v and you get the
depth of the drift column — which is exactly how §50 maps the cathode and found
that det3's column runs 26.5–29.5 mm across the chamber while det2's is a flat
30.5 mm.

Two properties make it the right handle here. It is **geometric, not
amplitude-based** — a bright flat flash and a dim flat flash both give a small
`q_uend`. And it is **already computed for every plane of every event**, so
nothing new has to be measured.

The 5 %-of-peak threshold is a deliberately crude choice, and the docstring says
why: "deliberately raw quantiles: the gap/column estimators that need a specific
definition build it downstream". §19.1's trap is the reason — NNLS profiles are
*sparse* (bins that want to go negative land on exactly zero), so any summary
that assumes a smooth profile misreads them. That already bit once: a per-bin
median over sparse profiles read the column as 24.7 mm and nearly got a chamber
disassembled.

#### What to build

A real drift column must cross the whole gap, so it must last a few hundred
nanoseconds. That bound already exists in the code as the `plausible` criterion
in `_candidate_score()` (`reco.py:187–198`):

```
U_MIN_NS = 250.0        # a real column lasts at least this long
U_MAX_NS = 1100.0       # ... and no longer than the gap allows
TAN_MAX  = 0.6
plausible = (U_MIN_NS <= fit.q_uend <= U_MAX_NS) and abs(fit.tan_theta) < TAN_MAX
```

An isochronous event fails the lower bound: all charge in one or two depth bins
means `q_uend` of order 60–120 ns, far below 250. So the rejection is already
*computed* — it is simply thrown away. Today `plausible` is used only to rank
candidate clusters within an event and is never written to the output table
(`row_from_fits`, `reco.py:302`), so no downstream analysis can cut on it.

Three steps, in order of value:

1. **Write it out.** Add `{plane}_q_uend` (already computed) and a
   `{plane}_isochronous` flag to the event table. One line each. This alone
   makes the cut available to every downstream analysis and costs nothing.
2. **Make the bound conditional rather than fixed.** `U_MIN_NS = 250` is a
   constant, and per F30's general complaint it should not be. The physical
   statement is "the column must span the local gap", i.e.
   u_end ≈ gap(x,y)/v — which varies by chamber (det2 30.5 mm, det3 26.5–29.5)
   and strongly with drift field (v runs 12 → 39 µm/ns across the drift scan, so
   the same 30 mm gap spans 770 ns at 1000 V and 2500 ns at 300 V). A fixed
   250–1100 ns window is a det3-at-1000-V window and will silently reject real
   tracks on a slow chamber. Derive it from `v_drift` and the gap.
3. **Add the direct measure, for the case the fit does not converge.** `q_uend`
   comes from a fit, and a pathological event is exactly where the fit is least
   trustworthy. A model-free companion — the spread of per-strip peak sample
   times across the window, which is ~0 for a flash and large for a track — is
   cheap and does not depend on the fit succeeding. Use it as the veto and
   `q_uend` as the confirmation.

One caution, the same one as F29: **a near-normal-incidence track is also short
in `q_uend`?** No — and this is worth stating clearly because it is the obvious
objection. A perpendicular track still deposits ionisation along the *whole*
drift gap; its charge arrives spread over the full ~800 ns, it just all arrives
on the *same strips*. Flatness in position is not flatness in time. That is
precisely why `q_uend` is the right discriminator and a multiplicity or
width-based cut is not: it separates "all the charge came at once" (a flash)
from "all the charge came on one strip" (a vertical muon), which no spatial cut
can do.

### F33 · Is `ftst` really a per-FEU quantity?
> *"Wait is the fst a per-feu quantity? Are we sure about that?"*

**CLOSED — yes, and both the code and the data confirm it.**

Code: `ftst` is read from each FEU's own tree, per event
(`io.py:83, 96` — `arrays(['eventId', 'amplitude', 'ftst'], ...)` inside
`FeuReader`, which is instantiated per decoded FEU file). It is returned per
event *per FEU*.

Data: `measure_dt_xy()` (§36) groups t0x − t0y by the **difference** of the two
FEUs' ftst values and gets two distinct, clean classes for det3 — **−7.65 ns**
(ftst diff 1) and **−16.01 ns** (ftst diff −5). If ftst were a global
per-event quantity that grouping would be meaningless and the classes would not
separate. So: per FEU, 10 ns units, and the X–Y electronics offset genuinely
depends on the relative clock phase of the two FEUs.

**One thing found while checking that is worth a look:** `select_pair()`
(`reco.py:270`) falls back to a hard-coded default of **−18.8 ns** for ftst
classes it has not seen — which matches *neither* of det3's two measured values.
Worth finding out where that number came from before pair selection is switched
on.

# HANDOFF — redo the run_145 target-imaging analysis on the corrected kernel

**Why this exists:** on 2026-08-19 the bench sharing kernel was corrected — the
production bundles carried an *inverted* ladder (the ±2 copy larger than the
±1, which cannot happen, since ±2 is reached only through ±1) and were refit
with `c2 = 0.6 × c1`. **run_145's beam reconstruction was seeded from the
pre-correction bench bundles and still carries the inverted kernel.** This file
is how to redo it. Nothing here is urgent for MPGD26 — the conference deck
ships with the old run_145 figures and a caveat (see §6).

Background: `mx_june_wft/R06_GATE_2026-08-19.md` (what changed and what it
cost), `wft-c1-floor-inverts-kernel` memory (why the kernel was wrong),
`sps_beam_test_26/analysis/sharing_kernel/` (the beam measurement, c2/c1 =
0.45 ± 0.02 model-free by cross-relation).

```bash
#    …then bring back the tarballs and stitch the tags into one table per arm:

../../.venv/bin/python ntof_tracking/condor/merge_beam_tags.py --arms A,B,D

# 3. the imaging + in-situ v (this is where the physics number comes from)
python -m ntof_tracking.run145_target_imaging --run run_145 \
    --subrun stat090_0000 --arms A,C,B,D \
    --slim /media/dylan/data/x17/slim/out_224670/ntof_hits_run_145_stat090_0000_224670.root

# 4. the note and the displays
python -m ntof_tracking.make_run145_note
python -m ntof_tracking.run145_wall_segment_3d     # the four-arm figure
```

The package builder refuses to ship a bundle with `c2 > c1`, or one still
stamped `w0_kw_stale` — both are exactly the defect this re-run exists to fix,
and both are silent once they reach a worker. `merge_beam_tags.py` refuses to
stitch tags that were reconstructed with different bundles, and refuses to
overwrite a table that is not already parked.

If the data *is* local (a fast link, or the desktop), the single-process route
still works and is simpler — `wft_beam.py` honours `WFT_BEAM_BASE`,
`WFT_BEAM_ANALYSIS` and `WFT_BENCH_ANALYSIS`, which is how B/C/D were done the
first time:

```bash
python -m ntof_tracking.wft_beam bundle --det A --run run_145 --v-drift 42.6
python -m ntof_tracking.wft_beam reco   --det A --run run_145 --jobs 6
```

## 4 · What to expect, and what to actually check

**The headline should barely move, but it must be MEASURED, not assumed.** The
published result is a back-projection *focus* and an in-situ drift velocity
obtained **by** focusing (`K_GRID` scan, `v_insitu = v_bundle / k_opt`). The
angle scale is therefore fitted, and a kernel change that shifts the fitted `w`
by a few per cent is largely absorbed into `k_opt` rather than into the image.
On the bench the same correction moved σ_θ(Y) by +0.06° and left position and
efficiency untouched.

So the checks that matter, in order:

1. **Does the spot still land inside the r ≤ 10 mm bore?** That is the claim.
2. **How much did `k_opt` move?** The published numbers are `v_insitu = 36.1
   µm/ns at k = 1.18` (note) / 36.3 (earlier memory). If `k_opt` moves by more
   than a couple of per cent, the "in-situ v" number on the deck and in the note
   changes and both must be updated.
3. **Per-arm agreement.** Four arms, one target: the arms should agree better
   after the correction, not worse. If B or D gets *worse*, suspect their refit
   basins (§5) before suspecting the correction.
4. **The 51 % external confirmation rate** (predicted SiPM segment AND plastic
   bar in time) — an independent handle that does not go through the fit's angle
   scale at all. It should not degrade.

## 5 · Traps

- **w0/kw: the published tables got them, just not where you would look.**
  The *superseded* prelim bundles carry no `w0`/`kw` at all — not by design,
  but because f9e18d2's `CalibrationBundle` dropped the field on the
  load→save round trip. `run145_target_imaging.apply_w0_kw` compensated by
  reading them back out of the **bench** bundle.json and correcting
  `tan` post-hoc. Since the 8-13 restore, `plane_fit` applies them in reco and
  stamps `angle_constants.applied`; the imaging script has a guard that skips
  the post-hoc pass on a stamped table (checked on the smoke output: the r06
  tables come back stamped, with r06's own w0/kw). So the operation is the same
  one, applied once, with the corrected constants — **do not add a second
  correction**, and do not be alarmed that the new prelim bundles now carry
  w0/kw when the old ones did not.
- **v_drift is a prior, not a measurement**, and the angle scale rides on it:
  Magboltz 90/10 @233 V/cm. Note `V_DRIFT_PRIOR = {A: 42.6, B: 34.0, C: 34.0,
  D: 36.0}` is **not** what the published run used — every arm was built at
  42.6 (`V_DRIFT_MAGBOLTZ`). Pin 42.6 on a re-run (`--v-drift 42.6`, which is
  the condor package's default) or `v_insitu = v_bundle / k` moves for a
  second reason and the comparison stops being about the kernel.
- **The gas is different.** run_145 is **Ar/Iso 90/10**; the bench bundles are
  95/5. `sigma_p0` and `Dp` are explicitly `not_revalidated` in the prelim
  provenance, and they are the gas-dependent ones. The kernel (a property of the
  resistive film, not the gas) is the part that legitimately transfers.
- **det2 and det7's r06 refits moved a long way** — kY 2.44 → 5.41 and
  2.51 → 5.60 (the latter against a fit bound of 6), σ_s 71 → 172 and 109 → 52 —
  while det3 stayed at 2.88. Arms B and D inherit those. If an arm behaves
  oddly, this is the first thing to look at, and re-fitting that detector with a
  wider `kY` bound is a legitimate response.
- **`run_79` has exactly the same problem** (`calib_bundle_prelim`, c2/c1 =
  1.14, seeded from det3) and the same fix. `RUN79_PRELIM_2026-07-30.md` is its
  record. Do them together if the fetch is happening anyway.
- **20 samples at 60 ns** on this run (`n_samples: 20`) against the bench's
  longer window — the sharing tail is more truncated here than on the bench,
  which is the direction that makes the *transferred* τ_s least reliable. The
  kernel's amplitudes transfer; its time constant is window-dependent and does
  not (see the memory note's "Delay: measurable, NOT transferable").
